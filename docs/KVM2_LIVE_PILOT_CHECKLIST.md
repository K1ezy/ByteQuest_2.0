# ByteQuest KVM 2 live pilot

Use this checklist for a supervised 30-student pilot. The VPS is the rehearsal target. Classroom readiness depends on the hosted test and approval in the last section.

## Local verification on 20 November 2026

- The production Linux backend image started in restricted mode and passed database readiness. The clean Next.js production build, 242 backend tests, and 168 frontend tests passed. Backend tests verified the Embedding 2 request format with a simulated Gemini provider.
- One synthetic 30-student run passed 17 cross-role checks, including 30 quiz submissions and 122 coding jobs, with zero unexpected responses. A separate mixed exam/practice run recorded all 60 exam items with no duplicate grades or XP awards. In that run, 95% of exam attempts graded within about 101 seconds. Most of that time was spent waiting in the grading queue. Both runs used local Supabase and a private Judge0 VM, with Gemini disabled.
- A disposable Supabase database upgraded successfully from the existing Sydney project's 14-migration baseline to all 38 migrations. The Sydney project still had 14 applied migrations at the time of the check. If it is selected, preview and apply the remaining 24 from the same source snapshot used by the app.

## Before provisioning

- Choose Hostinger KVM 2, Linux x86_64, and plain Ubuntu 22.04 LTS. Malaysia was available in the saved checkout. Verify the amount due and renewal term. Record the public IP and use key-based SSH with restricted admin access. [Hostinger VPS](https://www.hostinger.com/ph/vps-hosting) · [Judge0 Extra CE platform requirements](https://github.com/judge0/judge0/releases/tag/v1.13.1-extra)
- Use the purchased domain for the frontend and an `api.` subdomain for Caddy. Keep the web frontend on Vercel if the project qualifies for its current plan. This gives Judge0 and the API more room on a two-core server. Configure the Vercel project root as `frontend`. [Vercel terms](https://vercel.com/legal/terms)
- Use a dedicated hosted Supabase project for the rehearsal and pilot. Free is suitable for the synthetic rehearsal. The owner must accept the inactivity pause and schedule and verify encrypted offsite backups before keeping student records on Free. Choose a school-approved region and use the same project for Auth, PostgreSQL, Storage, and the API. [Supabase pricing](https://supabase.com/pricing) · [Restore runbook](PHASE7_BACKUP_RESTORE_RUNBOOK.md)
- Enable Gemini only for an eligible pilot. The Developer API terms restrict apps likely to be accessed by under-18s. Once a private paid key is available, use `gemini-3.5-flash-lite` for chat and `gemini-embedding-2` for PDF indexing and retrieval. Set `GEMINI_API_KEY` in the protected server environment. Set an AI Studio spend cap if offered and leave auto-reload off to use manual top-ups during the pilot. ByteQuest defaults to 40 chat requests per account each day. The chat reply ceilings are 350 tokens for quick facts, 600 for challenge hints, and 1,100 for explanations and debugging. Monitor provider usage for chat, PDF indexing, and other AI operations. [Gemini terms](https://aistudio.google.com/docs/terms#age-requirements) · [Gemini billing](https://aistudio.google.com/docs/billing) · [Tutor evaluation](verification/gemini-tutor-evaluation-2026-11-20.md)

## Configure and start the stack

1. Use the same release snapshot for the VPS, Vercel, and migrations. Record the source identifier or archive checksum. Link the CLI to the selected Supabase project, run `supabase db push --dry-run` and check the target and migration list, then use `supabase db push` without `--include-seed`. Load approved course content through the app and create separate synthetic accounts for hosted verification. [Supabase CLI reference](https://supabase.com/docs/reference/cli/v1/supabase-db-remote-commit) · [Deployment readiness](PHASE7_DEPLOYMENT_READINESS.md#deployment-order-after-the-decisions-are-made)
2. In Supabase Auth, set the frontend's HTTPS site URL and exact recovery/invitation redirects, configure approved SMTP, and test the sender with a synthetic account. Confirm the instructional PDF bucket is private and exercise course and role access using separate identities. Use the documented administrator provisioning path for instructors. [Supabase custom SMTP](https://supabase.com/docs/guides/auth/auth-smtp) · [Instructor provisioning](PRODUCTION_INSTRUCTOR_ACCESS.md)
3. Prepare Docker, swap, and the Judge0 host using the repository bootstrap and host preflight. Check the selected Judge0 image's cgroup requirements before using the optional GRUB setting, then verify them after reboot. Point the API DNS record at the VPS. Allow inbound HTTPS and HTTP for Caddy and restrict SSH to authorized administrators. Judge0, Redis and its PostgreSQL stay on internal Docker networks. Keep Judge0 callbacks and submission network access disabled. [Existing host setup](PHASE7_DEPLOYMENT_READINESS.md#production-settings-and-network-boundaries)
4. Create `infra/.env`, `infra/backend.prod.env` and `infra/judge0.prod.conf` from their examples with permission `600`. Use fresh, separate Judge0 database credentials, reviewed image digests and the project's TLS-required PostgreSQL connection string. Choose Supabase's session pooler on port 5432 if the VPS can reach the database over IPv4 only. Use one Judge0 execution slot to start. Verify the API and worker's 26-connection example ceiling against the selected database endpoint, leaving headroom for other clients. For initial checks with no AI key, set `GEMINI_ENABLED=false` and leave the key blank. Chat and PDF indexing both require Gemini in the current ByteQuest release. Reindex any carried-over PDFs with the updated Embedding 2 request format before checking retrieval. Keep research collection and ML shadow scoring off until separately approved. [Supabase PostgreSQL connections](https://supabase.com/docs/guides/database/connecting-to-postgres)
5. On the VPS, run these commands from `infra` after configuration. The public health check confirms HTTPS and database readiness. The role and grading checks below verify the rest.

   ```bash
   bash ./preflight-host.sh
   bash ./preflight-vps.sh
   docker compose --profile vps up -d --build
   bash ./smoke-vps.sh https://YOUR_API_HOSTNAME
   ```

6. Deploy the API first and verify that an authenticated request to `/api/v1/chat/status` returns the expected availability. Set the three values from `frontend/.env.production.example` in Vercel, then deploy the matching frontend. Use the public API URL ending in `/api/v1`, the correct Supabase project URL, and the browser-safe Supabase key. Add the frontend's exact HTTPS origin to the API CORS allowlist and confirm password reset returns to that same frontend. Roll the frontend and API back together if smoke tests fail.

## Decide whether to start the classroom pilot

- Saved chat history defaults off in the production environment example. Apply the chat history migration first. Verify the `bytequest-expire-chat-history` job in Supabase Cron and confirm that an expired synthetic chat disappears from the app and is purged. Publish the updated privacy notice, then enable `CHAT_HISTORY_ENABLED=true` on the VPS. Check regular history, Temporary Chat, and deletion with synthetic accounts before opening the feature to students.
- With synthetic accounts, test student sign-in and password recovery, course enrollment, staff-only access, an instructor publish, and one quiz and coding submission for each syllabus track. For the full pilot, verify the paid Gemini key with a private PDF citation and a coding hint. Confirm the same-tab draft survives refresh, chat stays paused through a timed exam when opened in another tab, and sign-out clears the saved conversation.
- Rehearse 30 simultaneous submissions on the actual VPS with the planned Python, C++, and Java workload if those languages are in scope. Include an exam deadline burst, mixed practice traffic, exam grading and result release. Agree acceptable grading wait and recovery targets with the instructor before running the test.
- Record HTTP errors, missing or duplicate grades, API and grading p95, queue age, CPU, memory, swap and disk. Require correct results, no lost or duplicate grades, and grading within the agreed target. If database checkout errors recur, investigate connection use and pool capacity first. If the issue is sustained CPU saturation and growing grading queues, evaluate a bigger VPS or a private second host for Judge0.
- Restore a database backup and private PDFs in an isolated test project. Assign an operator who can stop the exercise, roll back the release, or switch to the prepared local demo if hosted service fails. Obtain the institution's required approval before admitting real students or collecting study data.
