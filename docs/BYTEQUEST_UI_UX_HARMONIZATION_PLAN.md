# ByteQuest UI and UX harmonization plan

21 November 2026 · Proposed implementation for Student, Instructor, and Administrator

ByteQuest should tell each user **where they are, what needs attention, what their action will change, and what happens next**. The student experience should work comfortably on a phone from sign-in to a recorded grade. Instructors should be able to follow an activity from source material to publication and review. Administrators should be able to act on an issue from its overview without losing the course, account, or job that led them there.

## 2. How work moves through ByteQuest

1. **Administrator prepares access.** Create the course and assign instructors and student enrollments. The course page shows which setup steps remain and links directly to the affected roster or assignment. A person who signs up can open their account and track setup. Course enrollment is a separate step.
2. **Instructor prepares learning content.** In the selected course, create an activity directly or use an indexed PDF to generate a draft. Review saved content, verify applicable coding tests, preview the student view, and publish or schedule. Show the visible audience and opening time before and after publication.
3. **Student finds and completes the work.** Dashboard offers the next action. Quest Map or Workshop Activities shows eligible work with clear status. Practice, official submission, and grading have distinct controls and feedback. Exams show assignment, timing, save progress, and release status.
4. **Instructor reviews and releases results.** Activity Analysis, Student Progress, Gradebook, and Exam Results keep the same course and make their measures explicit. Exam release makes the permitted results visible to students. Workshop Progress presents workshop practice.
5. **Administrator handles operational exceptions.** System Overview leads to the affected course, user, material, or job. Monitoring provides service health, job status, and audit evidence within the administrator’s scope.

Use consistent names for the objects that cross roles. **Course** is the administrator-managed teaching unit with enrollment, scheduling, and official reporting. **Workshop** is the practice space joined with an invitation under the workshop’s access rules. **Programming track** is the configured language context. **Activity** is the instructor’s authored item. **Quest** is how eligible activity is presented in the student learning map. A **submission** is an official attempt in the grading flow. Use the activity title, course or workshop name, and consistent status across the handoff. Keep **Published**, **Available**, **Graded**, and **Released** distinct. Show dates with an unambiguous Asia/Manila time label where timing affects action. ## 6. Shared visual and interaction system

Adopt shared semantic tokens and components in the existing Next.js/CSS stack. Retain the ByteQuest brand, current accessibility preferences, and role-specific working patterns. A phone practice screen, a gradebook, and a monitoring table need different densities. They should still use the same labels, states, visual rules, and feedback.

| Requested area | Decision for ByteQuest |
| --- | --- |
| Shapes, proportions, and sizing | Start with 8 px corners for fields and buttons, 12 px for cards, and 16 px for dialogs. Use full rounding for avatars and compact status chips only. Align icon boxes to 16, 20, or 24 px, with the hit area sized separately. Give primary/secondary controls consistent heights. Use an approximate 44–48 CSS px minimum hit area for common touch actions, with 24 CSS px and its allowed exceptions as the WCAG AA floor. [W3C target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum) |
| Alignment, grid, and adaptive composition | Use a consistent content edge for page title, section titles, forms, and lists. Use start-aligned text and end-aligned comparable numbers. Document **columns**, **gutters** between columns, **outer margins**, and **spans**. Use a content-driven grid with one main column on narrow screens, up to two supporting regions on tablets, and a constrained desktop grid. Use fluid tracks and intrinsic wrapping. Wide tables and code may scroll in their own labeled region. [W3C reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow) |
| Padding, margins, whitespace, and vertical rhythm | Start from a 4 px base with 4, 8, 12, 16, 24, 32, and 48 px steps. Use shorter gaps within a related group and more space between sections. Start with 12–16 px horizontal content padding on small screens, 20–24 px on tablet, and 24–32 px on desktop. Give dense staff tables compact row spacing while preserving reading and touch targets. Prefer consistent vertical margins to empty decorative panels. |
| Elevation, blur, opacity, and visual balance | Use canvas, standard surface, raised control/overlay, and modal as the elevation levels. Distinguish content with spacing and subtle borders first. Use light shadows for floating or sticky controls and a stable scrim for dialogs. Keep blur out of normal content and timed tasks. Use opaque, readable text and surfaces. Use opacity for restrained transitions and layering, with stable contrast for required, explanatory, and disabled-state text. Align primary actions with the current task and avoid repeated large cards competing for attention. |
| Color palette, shades, tints, tones, and gray | Define neutral canvas, surface, divider, readable muted text, primary text, and contrast-mode equivalents. Use light neutral or subtle violet tints for grouping and selected surfaces, darker shades for text/interactive states, and desaturated neutrals to lower the emphasis of secondary content. Keep ByteQuest purple for primary action and selection, green for confirmed success, amber for attention, and red for error or destructive action. Pair semantic colors with text and where useful an icon. Reserve decorative track and reward accents for limited branded surfaces. Use chart series palettes with labels or patterns where needed. Assign by meaning and contrast, with no assumed universal color associations. |
| Contrast and modifying colors | Define explicit semantic pairs for normal, hover, pressed, focus, disabled, selected, and inverse states. Start with the current purple `#5927a6`, ink `#21163a`, and canvas `#f8f7fb`. Purple and white have about 9.27:1 contrast as a pair. The pale `#cec4dd` line against white is about 1.67:1 and belongs on decorative separators. Use at least 4.5:1 for normal text, 3:1 for WCAG large text and applicable non-text controls/indicators. Measure actual rendered combinations. Apply high contrast through tokens the components actually consume, respect forced colors, and use two-tone focus where needed. [Current tokens](../frontend/src/app/globals.css) · [WCAG 2.2](https://www.w3.org/TR/WCAG22/) |
| Font classification and pairing | Keep local ByteBounce for the wordmark and limited decorative identity. Use the existing system sans stack for functional headings, labels, and reading. Use existing monospace for code, invite codes, and machine identifiers. Apply tabular numerals where helpful for timers, grades, and numeric columns. Use weights and casing intentionally. Avoid adding a font download unless real-device testing shows a clear gain. |
| Type features, hierarchy, scale, and typesetting | Starting role scale in rem equivalents is 28–36 px for page titles, 22–26 px section titles, 17–20 px subsections, 16–17 px body/forms, and 13–14 px supporting text. Keep essential guidance at body size. Use about 1.2–1.3 line height for headings and 1.45–1.6 for prose. Aim for approximately 60–72 characters per line where there is room. Use sentence case and a single page H1 followed by meaningful headings. Let titles, course names, labels, long emails, and translated or enlarged text wrap. |
| Fixed and flexible elements | Keep header/navigation, exam timer, and context-specific actions fixed or sticky only where they improve orientation. Use flexible content below. Reserve real space for any fixed dock or footer, safe-area insets, and the on-screen keyboard. Collapse secondary sticky elements in short viewports. Use scroll margins and make focused elements fully visible in ByteQuest’s target layouts. [W3C focus not obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum) |
| Accessibility and feedback | Audit names, labels, grouping, landmark and heading order, focus order and restoration, skip links, current navigation, error association, and screen-reader announcements. Pair states with visible text. Announce important save/grade transitions once. Announce useful exam thresholds without reading every second. Allow password managers and paste where appropriate. Respect reduced motion and existing accessibility options. Add explicit keyboard/tap alternatives for drag and other gestures. |
| Component and state coverage | Consolidate page headers, section navigation, buttons and menu triggers, inputs, filters, chips, lists, tables, tabs, metric cards, dialogs, drawers, notices, and loading/failure/empty states. Cover loading, empty with a next action, stale, error, disabled with a reason, success, and restricted states as appropriate. Use visible messages for durable outcomes. Keep transient toasts for short feedback and use polite live announcements. Keep skeleton dimensions close to loaded content. |

Choose layout from available content width after the rail and insets. Preserve the current left/right setting and non-drag controls.

## 7. Contextual help and tooltips

### Choose the help treatment

1. **Rename an unclear action first.** Use **Recent course activity**, **Review drafts**, and **Copy invite code** where applicable. An icon still needs an accessible name even if it has a visual tooltip.
2. **Use visible inline copy for requirements and consequences.** Put field format, eligibility, deadline/time zone, save or submit effects, unsaved work, privacy/suppression, or grading/release rules beside the appropriate control. Include an action or recovery path when one exists.
3. **Use a tooltip for one short supplemental definition.** Opt in per control. Reuse and refine the existing shared tooltip infrastructure. Show on pointer hover and keyboard focus, keep focus on the trigger, use a distinct accessible description, and dismiss with Escape. Keep pointer-triggered help open while the pointer moves into it. Preserve descriptions already associated with the trigger. [W3C content on hover or focus](https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus) · [WAI-ARIA tooltip design guidance](https://www.w3.org/WAI/ARIA/apg/patterns/tooltip/)
4. **Use a labeled info button with a tap-open disclosure for shared terminology.** For example, **About pass rate**. Support keyboard, Escape, and tap outside where appropriate. Use a disclosure or accessible popover for longer explanations or links. Preserve native touch selection, scrolling, and dock gestures. Avoid automatic help on every named icon and one help trigger for every repeated table cell.
5. **Fit help to the viewport and scope.** Flip or clamp near dialog edges, rails, safe areas, zoom, or the soft keyboard. Close or reposition on scroll, resize, or navigation. Test Escape within a dialog so the help dismisses before the parent. Keep sensitive information and hidden grading data out of any help.

## 9. Verification and definition of done

- **Devices and input.** Check 320, 360, 375, 390, 412, and 430 CSS px portrait, short phone landscape around 800×360 or 844×390, 768–1024 px tablet, touch up to 1366 px, and desktop around 1280/1440/1920 px. Test physical iOS Safari and Android Chrome, plus lab browser keyboard and mouse. Cover left and right docking, touch targets, editor keyboards, pinching/zoom, safe area, slow links, and rotation.
- **Accessibility.** Use a WCAG 2.2 AA target for relevant flows. Check 200% browser/text enlargement and reflow at 320 CSS px, including the equivalent desktop zoom test. Run keyboard-only journeys, NVDA with a lab browser, and VoiceOver and TalkBack on phones. Test high contrast, forced colors, reduced motion, focus inside overlays, text spacing overrides, readable names, and state announcements. Use automated checks as part of this evidence. [WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- **Cross-role integrity.** Walk administrator assignment → instructor material/draft/verify/publish → learner joins or opens assigned work → official submission → staff grading and results release → learner sees eligible results → administrator inspects operational status. Use seeded roles in two courses, a wrong track, an unassigned instructor, an archived/closed workshop, held results, and a privacy-suppressed cohort. Practice and exam attempts stay separate. Gradebook and activity reports agree when measuring the same thing. Check saved work, one official attempt on retry, no hidden-case exposure, and no cross-role leakage.
