# ByteQuest 2.0 engineering and UX review

**November 14, 2026 · Overall 7/10 for a supervised 30-student pilot · Production verdict pending staging · Block graded timed exams pending deadline and job-claim fixes**

Reviewed the current Windows working tree and local Next.js, FastAPI, Supabase and Judge0 setup. The evidence includes fresh regression suites, a synthetic 30-student workload, rollback-only PostgreSQL checks, three browser role walkthroughs, and source and runbook review. Scores are rounded engineering judgments. A 7 means the core workflow is usable for the stated cohort with specific gaps, and a 9 requires repeatable evidence in its target environment.

| Area | Rating | Assessment |
| --- | ---: | --- |

## Findings

| ID | Severity | Evidence and impact | Correction and acceptance |
| --- | --- | --- | --- |
| BQ-01 | High | The rollback-only worker probe found that the 15-second grace-aware sweep left an attempt alone, while the live claim logic took it one second after its deadline. The answers endpoint also rejects writes at the deadline. An answer still in transit can be missing from the graded snapshot. [Claim and sweep](../backend/app/services/exam_worker.py#L21) · [Save deadline](../backend/app/api/exams.py#L444) | Define one server-authoritative cutoff and specify which in-flight writes qualify. Use the same policy across autosave, submit and automatic grading. Test on-time writes, in-flight writes, retries, expiry and disconnection at the boundary. |
| BQ-02 | High when scaling workers | The same rollback-only probe received the same attempt from two consecutive claims. The transaction releases its lock while status remains `grading`. The in-process guard limits a single worker. Multiple replicas can repeat provider work and waste time and capacity. The final write includes a status check under lock, so duplicate grades were not established. [Claim](../backend/app/services/exam_worker.py#L49) · [Final write](../backend/app/services/exam_worker.py#L108) · [In-process guard](../backend/app/services/submission_worker.py#L170) | Keep one grading worker until exams have a durable claim lease, bounded retries and stale-claim recovery. Verify one provider evaluation per live claim and recovery after a worker stops. |
| BQ-03 | High before production | A connection through the application's SQLAlchemy engine reported `postgres` with `BYPASSRLS` and `CREATEROLE` locally. A leaked runtime DSN exposes more than the app needs. Production login privileges were not inspected. [Database configuration](../backend/app/core/database.py#L20) · [Prior database review](../docs/DATABASE_REVIEW_2026-11-12.md#must-fix) | Use scoped API and worker credentials and a separate migration identity. In staging, verify required workflows and denial of direct Auth-schema reads and schema changes. |
| BQ-04 | Medium | Admin Overview showed “Services: Failed” and “2 of 4 services healthy” with historical submission failures and a deliberately disabled prediction service. The same local worker completed all 30 official jobs in the fresh run. The runner health code treats any failure in the last 50 records as failed when no jobs are active. [Health aggregation](../backend/app/services/monitoring.py#L63) | Show runner reachability, last successful job, queue age, recent failure rate and time of last check. Represent optional disabled services explicitly. Verify fresh success after old failures and stalled worker scenarios. |
| BQ-05 | Medium | Instructor Overview showed 8% average completion alongside “No graded attempts yet.” Course completion counts distinct attempted activities, while the latest-activity average excludes unsuccessful attempts and can become empty. The Performance table uses successful attempts for its completion count. [Summary query](../backend/app/services/workspace_queries.py#L266) · [Dashboard copy](../frontend/src/app/(workspace)/instructor/page.tsx#L176) | Define Started, Mastered and Average score, then align counts, denominators and eligibility across both views. Use “No scores for [activity]” when that is the scope. Test a mix of failures, passes and no attempts. |
| BQ-06 | Medium | Arena's sticky header measured 223 CSS px at 320 × 760. The editor started at about 919 CSS px on the initial document and required scrolling. The browser showed no page-level horizontal overflow at this width. Quest Map and Review Queue also fit at 390 px. [Shared header](../frontend/src/app/globals.css#L6303) · [Arena editor and controls](../frontend/src/components/arena.tsx#L660) | Use a compact runner header on narrow screens. Keep navigation, editor and Run sample easy to reach. Add a visible path between Problem, Editor and Results if needed. Test focus, 320 px reflow, zoom and soft-keyboard interaction. [WCAG reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) · [WCAG focus visibility](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html) |
| BQ-07 | Medium | Arena fetches the profile and full quest catalog after the workspace has loaded the profile. The catalog includes starter code and complete public quiz questions. Workshop listing performs two additional queries per group. These are code-confirmed costs. Their WAN and term-size impact remains unmeasured. [Arena requests](../frontend/src/components/arena.tsx#L226) · [Catalog](../backend/app/api/quests_gamification.py#L165) · [Workshop list](../backend/app/api/quest_groups.py#L84) | Reuse the workspace profile, return catalog summaries separately from per-activity detail, and batch workshop counts and activity IDs. Validate request count, transferred bytes and database query counts before and after. |
| BQ-08 | Medium | GitHub Actions runs backend pytest and frontend lint, types and build. It omits `npm test`, which locally runs the component and exam recovery tests. There is also a gap in repeatable, browser-to-worker exam acceptance. [Workflow](../.github/workflows/regression.yml#L34) | Add `npm test` to CI. Add one reproducible staging exam from assignment through reconnect, submission, grading, release and student review. Run it against a freshly migrated database and isolated accounts. |
| BQ-09 | Medium before enabling shadow scoring | The scorer reads current consent before feature reads and prediction insertion. Consent writers and the scorer lack a shared serialization boundary. Export coverage already exercises current-version consent. [Scoring](../backend/app/services/ml_predictor/shadow.py#L66) · [Consent writes](../backend/app/api/pilot.py#L311) · [Export test](../backend/tests/test_ml_export_consent.py) | Keep shadow scoring off until withdrawal has a concurrency test and clear retention behavior. Gate forecasts on approved out-of-cohort validation, calibration, support counts and faculty review. |
| BQ-10 | Low | Dashboard shortcuts repeat five destinations already in navigation and call Workshops “Quest groups,” while Quest Map uses “Join Workshop.” Instructor summary links still route via legacy `/faculty` redirects. [Dashboard shortcuts](../frontend/src/app/(workspace)/dashboard/page.tsx#L32) · [Redirects](../frontend/next.config.ts) | Use “Workshops” consistently and prioritize Continue quest, assigned deadlines and recent feedback. Update internal links to canonical routes. Retain redirects for bookmarked URLs. |

## Performance evidence

Fresh loopback run using the current API checkout and the running local grading worker and Judge0 installation. Windows, local PostgreSQL, 30 synthetic students, one published challenge, dashboard + autosave + sample enqueue + official enqueue + two-second polling. Sample acceptance was exercised. Completion metrics apply to official jobs.

| Metric | Observed |
| --- | ---: |
| Official jobs completed in 30 seconds | 30/30 |
| Official submission acceptance p50 / p95 | 0.234 s / 0.453 s |
| Official result median / maximum as seen by poller | 18.83 s / 26.45 s |
| Official attempts / distinct students | 30 / 30 |

The earlier documented mixed run recorded 0.234 s acceptance p95 and a 26.81 s maximum. Treat the two runs as evidence of meeting the classroom goal, with variation in acceptance times. The current measurements include poll observation delay. They do not isolate queue wait, Judge0 execution, or commit time. Monaco's self-hosted assets total about 24.4 MiB on disk, which is an asset inventory figure rather than a page transfer measurement. Collect compressed transfer, editor-ready time and web vitals on representative lab hardware before changing bundling. [Load driver](../backend/tests/load_test_local_synthetic.py) · [Earlier workload](../docs/BACKEND_RUNTIME_REVIEW.md#mixed-local-workload)

## Recommended sequence

1. **Before a graded pilot:** fix BQ-01 and add the exam acceptance run and frontend CI check from BQ-08. Keep the grading worker single-instance while addressing BQ-02. Rehearse disconnection at the deadline and worker recovery with a mixed quiz and code exam.
2. **Before public deployment:** scope database credentials, separate worker readiness from job history, check email confirmation and password recovery, verify Judge0 isolation and provider configuration in staging, and rehearse restoring both database and PDF objects. Track queue age, acceptance latency, completion latency, failed-job ratio, DB pool waits and success by language. [Deployment checklist](../docs/PHASE7_DEPLOYMENT_READINESS.md) · [Restore runbook](../docs/PHASE7_BACKUP_RESTORE_RUNBOOK.md)
3. **Next UX and performance pass:** fix course statistics, tighten the mobile runner header, and standardize the vocabulary. Then measure and remove duplicate fetches and query fan-out. Keep the existing PostgreSQL queue and dynamic Monaco load for the current cohort.
4. **AI and research:** keep grading independent of Gemini. Evaluate approved tutoring examples for hint usefulness, answer leakage, factual correctness and graceful outage handling. Require separate approval, verified withdrawal behavior, evidence beyond one small cohort and transparent intended use before presenting forecasts to staff.
